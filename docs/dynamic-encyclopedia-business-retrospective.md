## 一、面向运营的实际问题

### 1.1 运营实际开发问题

#### 1.1.1 当前是怎样的生产模式？

动态百科卡片的生产采用 **「模板包 + 子模板 + 自动生成」** 的三层生产模式：

```
父模板包 (dtp_dynamic_encyclopedia_card)
├── 通用子模板 ×5（摘要 / 时间线 / 关系图谱 / 对比辨析 / 可展开事实）
└── 垂直子模板 ×10（历史人物 / 电影 / 电视剧 / 文化词语 / 景区 五大垂类）
```

生产链路：
1. **运营输入词条**（如「李白」、「长安三万里」、「西湖」）
2. **词条引导向导** 自动识别分类（一级类 + 二级类）与置信度
3. **交互范式推荐** 从 8 个范式中推荐 1–3 个匹配的子模板
4. **BabeL-O 生成** 按子模板 `dataShape` + `rationale` + few-shot HTML 产出卡片
5. **spec review 质量门** 经过 27 条规则（11 条 error + 16 条 warning）审查
6. **多 Loop 修复** 通过 `loop_encyclopedia_spec_review`（qualityGates: static/spec/pixel）自动修复

#### 1.1.2 为什么会采用这样的生产模式？

采用这种生产模式的三个驱动力：

1. **规模化诉求**：动态百科词条数量级在万级以上，人工设计不可行，必须依赖自动化生成
2. **质量归一化**：通过统一的父模板包（788×492 PC / 380×456 WISE）和硬性归束（禁滚动、中文优先、禁外部脚本）保证所有产出的视觉与体验基线一致
3. **垂类适配**：通过「通用子模板 ×5 + 垂直子模板 ×10」的两层结构，兼顾复用度与垂类差异化（如历史人物需要关系图谱、景区需要地图 POI）

#### 1.1.3 当前生产模式的实际效果如何？

**已验证的部分**（基于 2026-07-08 硬性归束 v0.4 落地后的 WORKLOG）：

- ✅ 父模板包约束（尺寸、禁滚动、中文优先、交付安全）已完整落地
- ✅ spec review 27 条规则覆盖 4 个维度（既有约束、禁滚动、中文优先、垂类业务）
- ✅ Stage 1 → Stage 2 两阶段发布策略有效（warning → error 可控升级）
- ✅ `variationTemplateAssignments` 与 `designTemplatePackIds` 的兼容回退链路已修复
- ✅ 模板库排序、entryGuidance 渲染、产品模式切换在前端已贯通

**暴露的缺口**：

| 缺口 | 影响范围 |
|---|---|
| 4 个通用子模板（timeline/relation/compare/expandable）无 few-shot HTML | BabeL-O 生成时缺乏示例约束，产出稳定性下降 |
| 10 个垂直子模板无 HTML 示例 | 全部垂类生成依赖模型自主理解 dataShape，产出方差大 |
| democase mock 仅 8 类 | 推荐算法无法覆盖长尾词条 |
| 10 个垂直子模板 + 3 个交互范式 i18n 缺失 | 前端展示空白，运营无法识别推荐结果 |
| spec review Stage 1 规则仍为 warning | 新规约尚未强制生效，质量门松紧不一 |

#### 1.1.4 当前的生产模式到底有什么问题？

**核心问题集中在三个层面**：

1. **能力完整度不足**：1/5 通用子模板 + 0/10 垂直子模板有 HTML 示例，生产基线不稳
2. **覆盖度不足**：8 类 democase 远不能覆盖百科全量垂类，分类与推荐算法存在盲区
3. **强约束未生效**：Stage 1 16 条 warning 规则尚未升级到 error，质量基线未真正强制

### 1.2 用户实际生产（分发侧）

#### 1.2.1 当前用户是如何实际生产的？

用户侧的生产（分发）路径：

1. **运营/编辑在 Web 端选择词条** → 触发 `entryGuidance` 自动识别分类
2. **系统推荐 1–3 个子模板** → 用户从中选择或接受默认推荐
3. **BabeL-O 生成卡片** → 走 spec review + 多 Loop 修复
4. **运营/编辑二次审核** → 通过后投递到分发端（PC + WISE）
5. **用户在搜索 / 信息流场景消费卡片** → 单屏交付，无内部滚动

#### 1.2.2 为什么会采用这样的分发生产模式？

- **降低分发门槛**：用户（搜索用户）期望「打开即所得」，无需展开/折叠
- **保证视觉基线**：统一尺寸与硬性归束确保分发侧体验一致
- **匹配移动场景**：380×456 WISE 比例契合手机端阅读体验

#### 1.2.3 当前用户生产的实际产出如何？

| 维度 | 现状 |
|---|---|
| 卡片生产速率 | 自动化生成已跑通，但稳定性受 few-shot 缺失影响 |
| 质量分布 | 既有 11 条 error 规则保证底线，16 条 warning 规则收口未完成 |
| 垂类覆盖 | 5 大垂类已注册子模板，但仅历史人物/电影有实际产出路径 |
| 二次审核成本 | 运营反馈：模板少、需要手动调优、产出不稳定 |

#### 1.2.4 当前用户生产过程的反馈如何？

根据运营侧的实际体验反馈：

1. **「当前模式不具备实际的生产能力」**——运营人员普遍认为当前的模板模式仍处于「演示验证」阶段，距离规模化生产还有差距
2. **few-shot 不足导致产出方差大**——4 个通用子模板 + 10 个垂直子模板无 HTML 示例，运营需要多次重新生成才能获得可接受的结果
3. **i18n 缺失影响运营决策**——10 个垂直子模板无中文名/描述，运营无法直观判断推荐结果是否匹配词条类型
4. **垂类推荐覆盖不足**——8 类 democase 无法覆盖真实词条分布，长尾词条容易被错误归类或推荐错配子模板

#### 1.2.5 是否有必要迭代生产分发方式？

**结论：有必要，但应聚焦「在现有模式上加厚能力」而非「推翻重来」**。

理由：
- 三层架构（父包 / 通用子模板 / 垂直子模板）设计合理，硬性归束机制有效
- spec review + 两阶段发布策略已经为质量基线提供了工程化手段
- 当前主要问题是**能力厚度不足**而非**模式设计错误**

## 二、当前工作流以及其面向模版的实际问题

### 2.1 工作流为什么采用当前的模版模式？

当前工作流采用「**模板包 + 交互范式 + 推荐引擎 + 质量门**」的模版模式，核心原因：

1. **以模板承载结构化约束**：把硬性归束（尺寸、禁滚动、中文优先）下沉到父模板包，子模板聚焦垂类 dataShape，避免规则散落各处
2. **以交互范式解耦「做什么」与「怎么做」**：交互范式（如 `ip_relation_map`）作为推荐逻辑的唯一事实来源，与子模板通过 `compatibleTemplatePackIds` 单向关联
3. **以质量门保证产出底线**：spec review 27 条规则 + 静态/像素/规范三级 qualityGate，自动修复链路可控可回滚

### 2.2 当前模版模式有什么问题？

#### 2.2.1 模式上脱离生产实际

- **与当前运营实际迭代生产过程脱节**：模板系统的设计假设是「运营输入词条 → 自动识别分类 → 自动推荐 → 自动生成」，但实际运营反馈**当前模式不具备实际的生产能力**——需要补足 few-shot、补足 i18n、补足 democase 覆盖度才能进入规模化生产阶段
- **运营人员实际体验反馈**：当前模式还停留在「能用但不好用」的演示阶段，距离规模化生产还有差距

#### 2.2.2 功能上不具备生产标准

- **当前模版不具备强基线约束**：4 个通用子模板 + 10 个垂直子模板无 HTML 示例，生成阶段依赖 BabeL-O 自主理解 `dataShape` 与 `rationale`，产出方差大
- **不具备稳定生产质量**：spec review Stage 1 16 条 warning 规则尚未升级到 error，新规则尚未真正强制，质量基线松紧不一
- **探索度不足，无法依据有效抽卡产出有效的新结构样式**：缺乏「抽卡 → 评估 → 结构化沉淀 → 模板化」的有效链路，新结构样式难以从生成结果中沉淀为模板

#### 2.2.3 当前的硬性归束与质量门是有效的工程化基础

- 父模板包约束（尺寸、禁滚动、中文优先、交付安全）已完整落地
- spec review 27 条规则覆盖 4 个维度
- 两阶段发布策略有效
- 多 Loop 修复链路（`loop_encyclopedia_spec_review`）可控可回滚

### 2.3 当前工作流以及模版模式具有什么价值？

尽管存在上述问题，当前工作流与模版模式具有以下不可替代的价值：

| 价值点 | 具体体现 |
|---|---|
| **架构清晰、三层解耦合理** | 父包（硬约束）、子模板（垂类适配）、交互范式（推荐逻辑）职责清晰 |
| **质量门工程化** | spec review + 两阶段发布 + 多 Loop 修复，避免「规则不可控」 |
| **硬性归束基线** | 禁滚动、中文优先、禁外部脚本——保证所有产出视觉与体验一致 |
| **i18n 单向关联** | `compatibleTemplatePackIds` 作为唯一事实来源，避免双向不一致 |
| **可演进路径** | 通过 `packageChildren`、子模板注册、democase 扩展，可以渐进加厚能力 |

### 2.4 后续工作流工作应该如何进展？

后续工作流应聚焦**「能力加厚」与「基线收紧」**两条主线：

#### 主线一：能力加厚（短期内）

1. **补齐 4 个通用子模板的 HTML 示例**（timeline / relation / compare / expandable）
2. **生成首批 10 个垂直子模板的 HTML 示例**（优先历史人物 / 电影 / 电视剧）
3. **补齐 10 个垂直子模板的中文 i18n**（`历史人物·关系图谱` 等命名规范）
4. **补齐 3 个交互范式的中文 i18n**（`ip_causal_event_chain`、`ip_series_navigation`、`ip_route_guide`）
5. **扩展 democase 至更多垂类**（从 8 类扩展到 20+ 类，覆盖长尾词条）

#### 主线二：基线收紧（中长期）

1. **Stage 1 warning 规则升级到 error**：基于真实分布数据决策升级时机，升级时跑全量回归
2. **抽卡 → 评估 → 沉淀链路**：建立从 BabeL-O 产出中抽取新结构样式的工程化流程
3. **运营反馈闭环**：把运营的二次审核反馈沉淀为新的规则 / 模板 / i18n 资源
4. **真机 / 真场景压测**：在 PC 全屏预览、WISE 低分辨率、tab-bar 溢出、modal-overlay 点击穿透等真实场景中验证稳定性

## 三、方向策略问题

### 3.1 核心方向判断

经过本次复盘，我们对动态百科卡片业务的方向判断如下：

| 方向 | 判断 | 依据 |
|---|---|---|
| **继续走「模板化 + 自动化生产」路线** | ✅ 坚持 | 三层架构设计合理，硬性归束机制有效，是规模化生产的必由之路 |
| **「推翻模板、改为纯 LLM 自由生成」** | ❌ 不取 | 无法保证质量基线，分发侧体验会失控 |
| **「在现有模式上加厚能力」** | ✅ 核心路径 | 当前主要问题是能力厚度不足而非模式设计错误 |
| **「建立抽卡→沉淀链路」** | ✅ 关键探索 | 解决「探索度不足，无法沉淀新结构样式」的问题 |

### 3.2 三条核心策略

#### 策略一：能力厚度优先于模式翻新

**优先补足以下能力**：
- 5 个通用子模板的 HTML 示例（仅 summary 已有）
- 10 个垂直子模板的 HTML 示例（全部缺失）
- 10 个垂直子模板 + 3 个交互范式的 i18n 中文映射
- democase 扩展至更多垂类

#### 策略二：基线收紧与运营反馈双轮驱动

- **基线收紧**：把 Stage 1 warning 规则逐步升级到 error，强制质量基线
- **运营反馈闭环**：把运营的二次审核反馈结构化沉淀为规则 / 模板 / 资源
- **抽卡→沉淀链路**：从 BabeL-O 产出中抽取有效的新结构样式，工程化沉淀为模板

#### 策略三：分发侧体验与生产侧能力同步推进

- **分发侧**：在 PC 全屏预览、WISE 低分辨率、tab-bar 溢出、modal-overlay 等真实场景中验证稳定性
- **生产侧**：补足 few-shot、i18n、democase，降低运营二次审核成本

## 四、解决方案（解法）

### 4.1 短期解决方案（1–2 周）

#### 4.1.1 补齐通用子模板 HTML 示例

**目标**：5/5 通用子模板有 few-shot HTML

**行动**：
1. 基于 `case 垂类分类` 参考目录的 20 个可运行 HTML case
2. 为 timeline / relation / compare / expandable 四个子模板各生成 1–2 个高质量 HTML 示例
3. 纳入 spec review，验证稳定性

#### 4.1.2 补齐 i18n 中文映射

**目标**：10/10 垂直子模板 + 8/8 交互范式有中文名/描述

**行动**：
1. 按 `dtp_de_{垂类}_{交互类型}` → `历史人物·关系图谱` 格式补全 10 个垂直子模板 i18n
2. 补齐 `ip_causal_event_chain`、`ip_series_navigation`、`ip_route_guide` 三个交互范式 i18n
3. 验证前端 `c18n.templatePackName(...)` 与 `c18n.interactionParadigmName(...)` 渲染正常

#### 4.1.3 扩展 democase mock 数据

**目标**：democase 从 8 类扩展到 15+ 类

**行动**：
1. 基于垂类迭代规划文档的 20 个参考 case 提取真实词条
2. 补充 democase 数据结构（标题、别名、主分类、副分类、交互范式、preferredTemplateIds、关键词、摘要）
3. 验证推荐算法的覆盖度提升

### 4.2 中期解决方案（3–6 周）

#### 4.2.1 生成首批垂直子模板 HTML 示例

**目标**：10/10 垂直子模板至少各 1 个 HTML 示例

**行动**：
1. **第一优先级**：历史人物类（`history_person_relationship` + `history_person_event_chain`）
2. **第二优先级**：电影类（`film_cast_role_network` + `film_series_navigation`）
3. **第三优先级**：电视剧类（`tv_character_relation` + `tv_episode_chain`）
4. **第四优先级**：文化词语类（`cultural_phrase_relation_graph` + `cultural_phrase_origin_story`）
5. **第五优先级**：景区类（`scenic_spot_route_guide` + `scenic_spot_map_poi`）

#### 4.2.2 Stage 1 → Stage 2 规则升级

**目标**：基于真实分布数据，把成熟 warning 规则升级到 error

**行动**：
1. 收集 Stage 1 warning 规则的真实命中率
2. 对命中率低、误伤率高的规则做优化或下线
3. 对命中率稳定、误伤率低的规则升级到 error
4. 升级时跑全量回归测试，验证存量生成结果不误伤

#### 4.2.3 抽卡→评估→沉淀链路

**目标**：建立从 BabeL-O 产出中抽取新结构样式的工程化流程

**行动**：
1. 设计「抽卡评估维度」：结构合理性 / 视觉一致性 / 数据完整性 / 垂类适配度
2. 设计「结构样式沉淀流程」：抽卡 → 评分 → 模板化 → 注册子模板
3. 设计「运营反馈回流」：把运营二次审核结果结构化为可沉淀的资源

### 4.3 长期解决方案（持续）

#### 4.3.1 真机 / 真场景压测

**目标**：在真实分发场景中验证稳定性

**行动**：
1. PC 全屏预览 iframe 尺寸锁定 788×492 验证
2. WISE 端 380×456 在更低分辨率（如 300×360）下的 `@media` 查询调试
3. tab-bar 溢出行为验证（滚动的 tab-bar 是否违反禁滚动归束）
4. page-switcher 多页切换高度稳定性测试
5. modal-overlay 关闭后点击穿透问题验证

#### 4.3.2 接入真实 democase 数据

**目标**：从 mock 数据迁移到真实百科词条库

**行动**：
1. 与百科数据团队对接，获取真实词条分类与样本
2. 验证推荐算法在真实数据上的准确率与覆盖率
3. 持续优化 democase 数据结构与推荐规则

#### 4.3.3 运营反馈闭环

**目标**：把运营反馈工程化沉淀为规则 / 模板 / 资源

**行动**：
1. 建立运营反馈的结构化采集机制（评分、原因、改进建议）
2. 把高频反馈沉淀为新的 spec review 规则或硬性归束
3. 把有效的新结构样式沉淀为新的子模板或垂直子模板
4. 季度复盘运营反馈对系统能力进化的贡献

## 五、总结与行动项

### 5.1 核心结论

1. **当前模式设计合理**：三层架构（父包 / 通用子模板 / 垂直子模板）+ 硬性归束 + spec review + 多 Loop 修复的链路是规模化生产的正确路径
2. **当前主要问题是能力厚度不足**：4/5 通用子模板 + 10/10 垂直子模板无 HTML 示例，10/10 垂直子模板 + 3/8 交互范式无 i18n，democase 仅 8 类
3. **当前生产模式已具备工程化基础**：硬性归束、spec review、两阶段发布策略、可控修复链路都已落地
4. **运营反馈表明还需要加厚能力**：运营人员普遍认为当前模式还停留在「能用但不好用」的演示阶段，距离规模化生产还有差距

### 5.2 行动优先级

| 优先级 | 行动项 | 周期 |
|---|---|---|
| P0 | 补齐 4 个通用子模板 HTML 示例 | 1 周 |
| P0 | 补齐 10 个垂直子模板 + 3 个交互范式 i18n | 1 周 |
| P1 | 生成首批垂直子模板 HTML 示例（10 个垂类） | 3 周 |
| P1 | 扩展 democase 至 15+ 类 | 2 周 |
| P1 | Stage 1 → Stage 2 规则升级 | 持续 |
| P2 | 抽卡→评估→沉淀链路 | 4 周 |
| P2 | 真机 / 真场景压测 | 持续 |
| P3 | 接入真实 democase 数据 | 6 周+ |

### 5.3 关键风险与对策

| 风险 | 对策 |
|---|---|
| 运营侧投入不足，能力加厚进度滞后 | 把能力加厚拆解为可独立交付的小任务，每周同步进度 |
| Stage 1 升级到 error 时误伤存量结果 | 升级前跑全量回归，升级后监控真实命中分布 |
| 抽卡→沉淀链路工程化难度大 | 先以人工评估 + 模板化为 MVP，逐步工程化 |
| 真机 / 真场景问题暴露后修复成本高 | 在 dev / staging 环境持续压测，问题早发现早修复 |
